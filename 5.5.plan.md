## Phase 1: Back Navigation Fix (Issues #1 & #2)

### Problem Analysis

The app uses `StatefulShellRoute.indexedStack` with 5 branches (Dashboard, Plan, Record, Health, Profile). All shell branch routes share a single `AppShell` widget. Key findings:

1. **`AppShell`** (`app_shell.dart:11-52`) has **no `PopScope`** — system back on any tab exits the app
2. **`_PlanContent`** (`plan_screen.dart:70-74`) has a `PopScope(canPop: false)` that redirects to `/dashboard`, but it only wraps the active-goal state — `_NoPlanState`, `_PlanError`, `_PlanSkeleton` are unprotected
3. **Profile → Activities** (`profile_screen.dart:176`) uses `context.go('/activities')` which replaces the entire nav stack, so there's nothing to pop back to

### Fix 1a: Add PopScope to AppShell

**File:** `flutter/lib/presentation/widgets/app_shell.dart`

- Wrap the `Scaffold` in `PopScope(canPop: false)`
- In `onPopInvokedWithResult`, if `!didPop` and `navigationShell.currentIndex != 0`, switch to branch 0 (Dashboard)
- If already on branch 0, do nothing (don't exit the app)
- This single fix covers ALL shell tabs: Dashboard, Plan, Record, Health, Profile

```dart
return PopScope(
  canPop: false,
  onPopInvokedWithResult: (didPop, _) {
    if (didPop) return;
    if (navigationShell.currentIndex != 0) {
      navigationShell.goBranch(0);
    }
  },
  child: Scaffold(
    body: navigationShell,
    bottomNavigationBar: NavigationBar(...),
  ),
);
```

### Fix 1b: Remove PopScope from PlanScreen

**File:** `flutter/lib/presentation/screens/plan/plan_screen.dart`

- Remove the `PopScope` from `_PlanContent` (lines 70-74) since `AppShell` now handles it
- This also fixes the issue where `_NoPlanState`/`_PlanError`/`_PlanSkeleton` were unprotected

### Fix 1c: Fix all `context.go()` calls that should be `context.push()`

The following `context.go()` calls replace the nav stack, preventing back navigation:

**File:** `flutter/lib/presentation/screens/profile/profile_screen.dart`
- Line 176: Change `context.go('/activities')` → `context.push('/activities')`
- This preserves the nav stack so back gesture returns to Profile

**File:** `flutter/lib/presentation/screens/plan/plan_screen.dart`
- Line 92: Change `context.go('/goals/${goal.id}')` → `context.push('/goals/${goal.id}')`
  - Currently: navigating from Plan to Goal detail breaks back gesture
- Line 32: Change `context.go('/goals/new')` → `context.push('/goals/new')`
  - Currently: navigating from no-plan state to Goal wizard breaks back gesture

**File:** `flutter/lib/presentation/screens/goals/goal_list_screen.dart`
- Line 114: Change `context.go('/goals/${goal.id}')` → `context.push('/goals/${goal.id}')`
  - Currently: navigating from Goal list to Goal detail breaks back gesture

**NOTE:** `activity_detail_screen.dart:36` uses `context.go('/activities')` but has a safe fallback: `if (context.canPop()) { context.pop(); } else { context.go('/activities'); }` — this pattern is correct and does NOT need changing.

### Design Decision: Back on Root Tab

`canPop: false` with no-op on branch 0 means **the app will never exit via system back**. This is a deliberate UX choice — the user explicitly wants back to navigate between tabs, not exit. This is non-standard Android behavior but matches the app's navigation model. If this is undesirable, add `SystemNavigator.pop()` in the branch-0 case.

## Phase 2: Supplement System Fixes (Issues #3 & #4)

### Problem Analysis

**Take All Race Condition:** Three "Take All" implementations all use the same broken pattern:
```dart
for (final s in stackUntaken) {
  ref.read(supplementListProvider.notifier).toggle(s.id); // NOT awaited
}
```
Each `toggle()` call (health_providers.dart:103-121) is async: it reads `dailyHealthProvider`, makes an HTTP POST, then invalidates 3 providers. Without awaiting, all toggles fire concurrently, read the same stale state, and cause provider invalidation thrashing.

**Stack Rename:** Stacks are displayed using the raw `stackId` string from the `Supplement` entity. There is no rename UI, no `updateStack` method, and no API call for renaming.

### Fix 2a: Add sequential `takeAll` method to provider

**File:** `flutter/lib/presentation/providers/health_providers.dart`

Add a new `takeAll(List<int> ids)` method to the `SupplementList` notifier:
```dart
Future<void> takeAll(List<int> ids) async {
  for (final id in ids) {
    await toggle(id);
  }
}
```

This ensures each toggle completes (API call + provider invalidation) before the next one starts.

**Why sequential `await` works:** `toggle()` uses `ref.read(dailyHealthProvider(today).future)` (one-shot read, not `ref.watch`). After toggle #1 calls `ref.invalidate(dailyHealthProvider(today))`, the provider is marked stale. When toggle #2 calls `ref.read(dailyHealthProvider(today).future)`, it re-reads the provider and awaits the fresh value from the API. So sequential awaiting correctly sees each prior toggle's state change.

**No `.g.dart` regeneration needed** — `takeAll` is a method on an existing notifier, not a new provider.

### Fix 2b: Update all "Take All" handlers to use `takeAll`

**File:** `flutter/lib/presentation/screens/health/supplements_screen.dart`

- `_buildNextPrompt` onTakeAll (lines 171-175): Change from:

  - **Option A (preferred):** Change `_GroupedSupplementList.onTakeAll` from `void Function(List<Supplement>)` to `VoidCallback` and have the parent widget pass a pre-computed `takeAll` closure
  - **Option B:** Keep the callback signature but have the parent call `takeAll` instead of looping `onToggle`

  **Option A implementation:**

## Phase 3: Data Alignment, Marathon Graph, Health Sync (Issues #5, #6, #7)

### Issue #5: Dashboard vs Analytics TSB/CTL Misalignment

#### Problem Analysis

**Dashboard** reads from `GET /dashboard` → `DashboardResponse.stats` (AnalyticsStats with ctl/atl/tsb) — NO validation, raw pass-through.

**Analytics** reads from `GET /analytics/stats` → `AnalyticsStats` with a fallback: if `atl == 0 || ctl == 0`, fetches `GET /analytics/history` (30 days) and uses last history point's values.

These are **two completely different backend endpoints** with no guarantee of consistency. The dashboard endpoint returns CTL=42/TSB=5 while the analytics endpoint (with or without fallback) returns CTL=10/TSB=-0.4.

Additionally, `analytics_repository_impl.dart:78` hardcodes `ctlRunning: 0.0` in history parsing, losing running-specific CTL data.

#### Fix 3a: Unify TSB/CTL/ATL source — Dashboard reads from Analytics provider

**Root cause detail:** The `/dashboard` endpoint returns CTL/ATL/TSB that differ from `/analytics/stats`. The analytics provider has a fallback (history lookup when values are zero), but the dashboard endpoint returns **non-zero but incorrect** values (CTL=42 vs actual CTL=10). Simply falling back when zero won't help — we must always prefer analytics stats.

**Approach:** Have `_DashboardContent` (already a `ConsumerWidget` at `dashboard_screen.dart:51`) watch `analyticsStatsProvider` and override the CTL/ATL/TSB from `DashboardResponse.stats` with the validated analytics values.

**File:** `flutter/lib/presentation/screens/dashboard/dashboard_screen.dart`

In `_DashboardContent.build()`:
```dart
final analyticsStats = await ref.watch(analyticsStatsProvider).value;
final effectiveStats = data.stats.copyWith(
  ctl: analyticsStats?.ctl ?? data.stats.ctl,
  atl: analyticsStats?.atl ?? data.stats.atl,
  tsb: analyticsStats?.tsb ?? data.stats.tsb,
);
_StatsCard(stats: effectiveStats, syncStatus: data.syncStatus),
```

**Why this works:** `_DashboardContent` is already a `ConsumerWidget`. `_StatsCard` remains a `StatelessWidget` — no type change needed. The `AnalyticsStats` class (from `dashboard_entities.dart`) is the same type used by both dashboard and analytics providers. `DashboardResponse.stats` is a freezed class with `copyWith`.

**Additional import needed:** `import 'package:runflow_flutter/presentation/providers/analytics_providers.dart';`

**Additional bug — `ctlRunning: 0.0` hardcode:** `analytics_repository_impl.dart:78` hardcodes `ctlRunning: 0.0` when parsing history, losing running-specific CTL data. This should be parsed from the API response if the field exists, or at minimum tracked as a follow-up issue.

### Issue #6: Marathon Shape Combined Graph

#### Problem Analysis

The current `_MarathonShapeSection` (analytics_screen.dart:579-655) is a `LinearProgressIndicator`. A `Vo2ShapeTrendChart` widget exists but has a critical bug at lines 37-39: it replots the **current** VO2max and marathon shape at every history date point, producing two flat horizontal lines.

The `FitnessHistoryMetrics` entity (analytics_entities.dart:1-45) only has `ctl`, `atl`, `tsb`, `ctlRunning` — no `marathonShape` or `vo2max` fields. The history API only returns CTL/ATL/TSB per date.

**However**, the `CombinedAnalyticsChart` (combined_analytics_chart.dart) already includes a VO2max line (also with the flat-line bug at line 234). The fix for the flat-line bug requires either:
- (a) Backend adds `marathonShape` and `vo2max` to the history endpoint response, OR
- (b) We derive approximate historical VO2max from CTL values (since VO2max correlates with fitness)

**Approach (b)** is pragmatic for now:
- Derive approximate historical VO2max: `vo2max ≈ 30 + (ctl / 2)` (rough estimate based on training literature)
- Use the history data's CTL values to plot an estimated VO2max trend
- Plot marathon shape as: `shape = (currentShape / currentCTL) * historicalCTL` (linear approximation)
- Show a note that these are estimates

OR (simpler approach that works with existing data):
- Replace `_MarathonShapeSection` with a dual-axis line chart using the existing `FitnessHistory` CTL/ATL/TSB data
- Left Y-axis: Marathon Shape (derived from CTL ratio) + VO2max (current value as reference line)
- Actually, the simplest correct approach: just show the existing CTL line (which IS the fitness/marathon shape proxy) alongside the current VO2max as a reference
- Label it "Marathon Shape & Fitness Trend"

**Chosen approach:** Replace the `LinearProgressIndicator` with a proper `LineChart` using existing `FitnessHistory` CTL data (as marathon shape proxy) plus current VO2max as horizontal reference line. This avoids needing backend changes.

**IMPORTANT NOTE:** The CTL-derived approximations (`vo2max ≈ 30 + (ctl / 2)` and `shape = (currentShape / currentCTL) * historicalCTL`) are PLACEHOLDER formulas. They are NOT scientifically validated. These should be clearly labeled as estimates in the UI, and replaced with real data when the backend adds `marathonShape` and `vo2max` fields to the history endpoint.

**File:** `flutter/lib/presentation/screens/analytics/analytics_screen.dart`

- Replace `_MarathonShapeSection` implementation
- Watch `analyticsHistoryProvider` for time-series data
- Build `LineChart` with:
  - Line 1: CTL over time (color: primary, labeled "Fitness/Shape")
  - Line 2: Current marathon shape as horizontal dashed reference line
  - Line 3: Current VO2max as horizontal dashed reference line (scaled to fit)
- Match existing `_FitnessChart` style (fl_chart patterns, curved lines, tooltips)
- Keep the calibration button

## Known Limitations / Follow-ups

1. **Historical VO2max/marathon shape** — Currently estimated from CTL using PLACEHOLDER formulas. Backend should add these to the history endpoint for accuracy. Formulas are clearly labeled in code as approximate.
2. **Stack rename** — Uses client-side `SharedPreferences` mapping. Backend has no PUT/PATCH for supplements. If an update endpoint is added later, migrate to API calls.
3. **`Vo2ShapeTrendChart` widget** — Exists but is unused and buggy. Either fix and use it, or delete it in favor of the new inline chart.
4. **`CombinedAnalyticsChart`** — Also has the flat-line VO2max bug (line 234). Should be fixed in a follow-up.
5. **i18n** — ~13 hardcoded English strings from Phase 4.5 work. Should be localized in a follow-up.
6. **`ctlRunning: 0.0` hardcode** — `analytics_repository_impl.dart:78` hardcodes running CTL to 0. Backend history response may contain this data. Should be parsed from response when available.
7. **`canPop: false` on root tab** — App cannot be exited via system back. This is intentional. If users report this as unexpected, add `SystemNavigator.pop()` on branch 0 with a double-tap-to-exit pattern.
