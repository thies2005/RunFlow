## 3. Wave 1: Domain Engines, Data Models & Parity

### 3.1 WebPlanEngine Cross-Platform Parity
- **Test Suite**: `android/app/src/test/java/com/runflow2/app/domain/plan/WebPlanEngineParityTest.kt`
- **Fixtures**: 31 JSON fixtures located in `android/app/src/test/resources/plan_fixtures/` covering 5k, 10k, Half Marathon, Marathon, 50k, 50M, 100k, 100M, Sprint Tri, Olympic Tri, Half Ironman, Full Ironman, Backyard Ultra, and Time-based plans.
- **Key Formulas Aligned**:
  - **Cycling FTP calculation from VDOT**:
    $$\text{Bike FTP (W)} = \frac{\text{VDOT} - 7}{10.8} \times 0.75 \times \text{weightKg}$$
    Both `Web/src/lib/plans/index.ts` and `android/app/src/main/java/com/runflow2/app/domain/plan/WebPlanEngine.kt` use this exact formula with fallback `weightKg = 70.0`.
  - **Taper Long Ride Reductions**:
    Multi-sport taper weeks use exact scaling factors:
    - 3 weeks out: `0.70`
    - 2 weeks out: `0.55`
    - Race week: `0.40`
  - **Gym & Strength Descriptions**:
    Standardized across all generators to `"Strength & Gym: 45min"`.
  - **DST-Safe Week Calculations**:
    Replaced raw millisecond division (`ms / (7 * 86400000)`) with calendar-day math: `Math.ceil(calendarDays / 7)` in `Web/src/lib/plans/index.ts` to prevent timezone/daylight saving drift.

### 3.2 Binary FIT File Exporters (`.fit`)
- **Specification**: Garmin Flexible and Interoperable Data Transfer (FIT) Protocol.
- **Implementations**:
  - Android: `android/app/src/main/java/com/runflow2/app/core/export/PlanFitExporter.kt`
  - Web: `Web/src/lib/plans/fit-export.ts`
  - Web Route: `POST /api/mobile/v1/workouts/[id]/export/fit`
- **Output Format**:
  - File Header: 14 bytes (Header size 14, Protocol v2.0, Profile v21.60, Data size, `.FIT` signature, 16-bit CRC).
  - File ID Message: Manufacturer Development (255), Product 1, Type 5 (Workout).
  - Workout Message: Sport type (1=Running, 2=Cycling, 5=Swimming), capabilities, number of steps.
  - Workout Step Messages: Intensity (Active, Warmup, Cooldown, Rest), Duration Type (Time vs Distance), Target Type (Pace, Heart Rate, Power, Open), Target Values (scaled).
  - Checksum: 16-bit CRC computed across all data records using CRC-16-CCITT polynomial table.

### 3.3 Offline Backup Manager (`.runflow.json`)
- **File**: `android/app/src/main/java/com/runflow2/app/core/export/LocalBackupManager.kt`
- **Test**: `LocalBackupManagerTest.kt`
- **Schema**:
  ```json
  {
    "version": 1,
    "exportedAt": "2026-10-30T20:00:00Z",
    "athlete": { "vdot": 50.0, "ftp": 250, "maxHr": 190, "restHr": 50 },
    "goals": [ ... ],
    "workouts": [ ... ],
    "activities": [ ... ],
    "settings": { ... }
  }
  ```
- **Capabilities**:
  - Complete export to JSON string or file stream via Android Storage Access Framework (SAF).
  - Two import modes: `Merge` (updates existing, inserts missing) and `Overwrite` (wipes tables and restores exact state).

### 3.4 SmartScheduler & Readiness Adaptations
- **Scheduler**: `android/app/src/main/java/com/runflow2/app/domain/plan/SmartScheduler.kt` enforces a minimum of 48 hours between quality/key sessions (Intervals, Repetitions, Tempo/Threshold, Long Runs).
- **Adaptation Rules** (`ReadinessScoring.kt`, `ReadinessAdaptationTest.kt`):
  - When athlete Readiness Score $< 65$:
    - Hard interval workouts are automatically converted to Zone 2 Easy / Recovery runs or optional rest.
    - Planned TSS is scaled down by $35\% - 50\%$.
    - The workout record records `adaptationType = "READINESS_DOWNGRADE"`.

### 3.5 Compliance Calculator
- **Files**: `android/app/src/main/java/com/runflow2/app/domain/plan/ComplianceCalculator.kt` and `Web/src/lib/plans/compliance.ts`.
- **Tiers**:
  - **Green (Completed)**: $\ge 80\%$ duration or TSS achieved.
  - **Yellow (Partial)**: $50\% - 79\%$ duration or TSS achieved.
  - **Red (Missed / Low)**: $< 50\%$ duration achieved or workout skipped.

### 3.6 Best Efforts & Peak Power Engine
- **File**: `android/app/src/main/java/com/runflow2/app/core/math/BestEffortsEngine.kt`
- **Distances (Running)**: 400m, 800m, 1k, 1mi, 5k, 10k, 15k, 10mi, Half Marathon (21.097km), Marathon (42.195km).
- **Durations (Cycling MMP)**: 5s, 15s, 30s, 1m, 2m, 5m, 10m, 20m, 30m, 60m.
- **Algorithm**: Rolling window scan across activity stream records (`distance`, `time`, `watts`) in $\mathcal{O}(N)$ using index pointers.

### 3.7 Database Schema: Room v16 (Android)
- **File**: `android/app/src/main/java/com/runflow2/app/data/db/AppDatabase.kt`
- **Migration `MIGRATION_15_16`**:
  ```sql

  ALTER TABLE workouts ADD COLUMN adaptationType TEXT DEFAULT NULL;
  ```

## 5. Critical Gotchas, Edge Cases & Lessons Learned

> [!WARNING]
> **Client vs Server Module Boundaries in Next.js (CRITICAL)**:
> In Next.js 15, files marked with `'use client'` cannot import modules that depend on Node-native packages (`pg`, `dns`, `net`, `fs`).
> - **The Problem**: `fitnessCache.ts` imported `@/lib/db`, which imports `pg`. When `ActivityList.tsx` (a client component) imported `resolveActivityEffectiveTss` from `fitnessCache.ts`, Next.js bundled `pg` into the browser bundle and crashed with:
>   `Module not found: Can't resolve 'dns'` / `Can't resolve 'fs'`.
> - **The Solution**: Always keep pure mathematical helpers in dedicated files with zero database imports. We created `Web/src/lib/metrics/effectiveTss.ts` to house `resolveActivityEffectiveTss`. Never re-introduce DB imports into this file.

> [!IMPORTANT]
> **CSRF Validation in Web Test Suites**:
> `Web/src/lib/security/csrf.ts` enforces HMAC-signed nonces (`${nonce}.${signature}`).
> - Tests mocking CSRF authentication headers or cookies must **not** pass raw random strings (e.g. `'tok-abc'`). They must call `generateCsrfToken()` from `Web/src/lib/security/csrf.ts` or the request will fail with HTTP 403 Forbidden.

> [!NOTE]
> **Android Working Directory & Gradle Rules**:
> - All Android build and test commands **must** have their working directory set to `android/` (e.g. `cd android && ./gradlew testDebugUnitTest`).
> - Release signing reads `android/key.properties`. If this file is missing, `assembleRelease` will build an unsigned APK.
> - Never run debug APK builds when release is requested.

> [!TIP]
> **Gradle Build Cache & Task Out-of-Date State**:
> When verifying freshly committed code changes for binary deliverables, running `./gradlew assembleRelease` can sometimes resolve tasks as `UP-TO-DATE` or `FROM-CACHE`. Always run:
> ```bash
> ./gradlew clean assembleRelease --no-build-cache --rerun-tasks
> ```
> when producing the final deployable APK artifact to ensure all tasks execute from scratch.

## 8. RunFlow v2.8.1 Widened Master Implementation & Remediation

Following the v2.8.0 release, a comprehensive codebase and interaction audit identified 6 core sync, activity linking, and analytics display items, resolved in v2.8.1:

### 8.1 Fast-Push Direct Mutation Synchronization & Dynamic `linkedActivityId` Resolution
- **Problem**: Local database edits (workout edits, profile updates, cycling FTP updates, activity saves, manual daily readiness entries) queued outbox items into `syncQueueDao` but never triggered immediate background syncing, leaving the `"N pending sync"` badge stuck until app restart or manual sync. When linking newly recorded local activities (`serverId == null`), `PatchWorkoutRequest.linkedActivityId` sent a local UUID to the server resulting in HTTP 404 dead-lettering.
- **Resolution**:
  - Implemented `SyncManager.triggerFastPush(reason)` with a 250ms debounce and fast-push execution (`pushPendingNow`) which drains outbox items and uploads dirty readiness entries without blocking on full activity or plan pulls.
  - Registered `RunFlowRepository.onMutationCommitted` to trigger `triggerFastPush()` after every repository write.
  - In `SyncManager.handleOutboxItem(TYPE_WORKOUT_UPDATE)`, dynamically resolved `req.linkedActivityId` via `activityDao.byId(id)?.serverId`. If `serverId == null`, deferred the update (`IOException`) until the local activity is uploaded by `TYPE_ACTIVITY_CREATE`.
  - In `SyncManager.pullPlans()`, resolved server `linkedActivityId` to local `activityDao.byServerId(serverId)?.id ?: serverId`.

### 8.2 Strict 1:1 Activity-to-Workout Linking & Reassignment
- **Problem**: `CompleteWorkoutSheet.kt` filtered candidates only by date window without checking whether an activity was already claimed by another workout, leading to duplicate assignments.
- **Resolution**:
  - In `CompleteWorkoutSheet.kt`, collected `goalWorkouts` to construct a claimed activities map (`act.id` and `act.serverId`).
  - Filtered out already-linked activities by default, and added a compact toggle button: `"Show already-linked activities (N)"` allowing deliberate reassignment with automatic unlinking of previous workouts.
  - Updated `WorkoutMatcher.matchWorkouts()` with `claimedActivityIds` so suggestions never re-suggest already claimed activities.

### 8.3 Context-Aware Home Screen (`Today`) Workout Actions
- **Problem**: Uncompleted workouts on the Today dashboard only displayed a single `"Start workout"` action button, even for non-recordable types (`STRENGTH`, `SWIM`, `CROSS_TRAIN`, `REST`, indoor MyWhoosh rides) with no way to complete or link them from the Home screen.
- **Resolution**:
  - Introduced `WorkoutEntity.canRecordInApp(type)` helper detecting outdoor GPS-recordable runs and rides.
  - For in-app recordable workouts: side-by-side **`[ ▶ Start ]`** and tonal **`[ ✓ Complete ]`** buttons.
  - For non-in-app workouts: full-width tonal **`[ ✓ Complete ]`** button launching `CompleteWorkoutSheet`.
  - For completed workouts: displays `InfoChip` with the linked activity name and a **`[ Relink 🔗 ]`** button.

### 8.4 Analytics Spacing, Heading Weights & Restored Visual Diagrams
- **Problem**: `SectionTitle` in `Common.kt` contained a greedy `fillMaxWidth()` row that starved sibling badge chips, causing text to wrap vertically (10-15 lines tall). Several key visual diagrams were removed in the 4-tab refactor.
- **Resolution**:
  - Refactored `SectionTitle` with conditional `weight(1f, fill = false)` when `trailing != null` and unwrapped text when `trailing == null`.
  - Added `"Log / Edit"` button to `DailyReadinessCompositeCard` in `RecoveryAnalyticsTab.kt` launching `DailyFormSheet`.
  - Restored 5 removed diagrams:
    1. **Overview**: PMC range filter chips (`90d`, `180d`, `1Y`) and interactive `CTL / ATL / TSB` metric bars with peak percentage toggles.
    2. **Overview**: 7-Zone Heart Rate Time-in-Zone Distribution chart (`ZoneDistribution(bundle.zoneSeconds)`).
    3. **Run**: Running Load (PMC) chart (`bundle.runFitnessSeries`) with dedicated range chips and metric toggles.
    4. **Run**: Race Predictions Card (`5K`, `10K`, `Half Marathon`, `Marathon`) comparing shape-adjusted times vs. ideal VDOT.
    5. **Run**: Visual pace curve canvas on Running Best Efforts and `This Week` vs `12-Week Avg` volume tiles.

### 8.5 Polished MMP Curve with Stream Backfill & Hyperbolic Decay Fallback
- **Problem**: Mean Maximal Power (MMP) graphs collapsed into a flat horizontal line when 1Hz streams were not cached locally.
- **Resolution**:
  - Added background activity stream backfill in `RunFlowRepository.kt` (`fetchAndCacheStreams`) prioritizing rides with power.
  - Replaced flat-line fallback in `AnalyticsEngine.extractPowerMmp` with a physiologically realistic Monod-Scherrer hyperbolic power decay model capped at `dur <= movingTimeSec`.
  - Redesigned `CyclingMmpCurveCard` with padded Y-axis labels, smooth quadratic curve with vertical gradient fill, dashed 1Y peak line, interactive drag scrubber with live readout pill, and log-spaced duration labels.

### 8.6 Consolidated Heart Rate & Power/FTP Zones in `HrZonesScreen.kt`
- **Problem**: Cycling FTP and the 7-zone Coggan table were rendered directly in `AthleteScreen.kt`, duplicating settings and leaving `HrZonesScreen.kt` without cycling power models.
- **Resolution**:
  - Removed `CyclingFtpCard` and power tables from `AthleteScreen.kt`, leaving a single clean summary line in the "Body & thresholds" card.
  - In `HrZonesScreen.kt`, added a 2-tab `SingleChoiceSegmentedButtonRow`:
    - **Tab 0 (Heart Rate)**: Base HR thresholds quick-edit row (Max HR & Resting HR), Karvonen Auto toggle, manual Z1..Z6 sliders, and 7-zone HR preview bars.
    - **Tab 1 (Cycling Power)**: Cycling FTP Configuration Card (Manual FTP / Active eFTP, W/kg, Auto-estimate FTP switch, inline manual FTP editor + Save button) and Coggan 7-Zone Power Model Card (Z1..Z7 breakdown with colored pills, % FTP ranges, calculated watt boundaries, and proportional visual preview bars).
  - Wired `onOpenZones = { navController.navigate(Routes.HR_ZONES) }` in `RunFlowRoot.kt` and connected `"Edit Zones →"` navigation buttons from Analytics tabs.
