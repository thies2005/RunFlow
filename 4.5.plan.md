## Phase 1: Critical Bug Fixes

### 1.1 Goal Deletion Crash - Riverpod State Management
**Priority:** CRITICAL
**Bug:** `Cannot use the Ref of goalsProvider after it has been disposed`
**Root Cause:** `Goals.deleteGoal()` in `goal_providers.dart:37-41` calls `refresh()` after the async `repo.deleteGoal(id)` call. If the provider is rebuilt/disposed during the async gap, calling `ref.read()` crashes.

**Files to modify:**
- `flutter/lib/presentation/providers/goal_providers.dart`

**Implementation:**
1. Add `ref.mounted` check after the async gap in `deleteGoal()` — `ref.mounted` is available in `flutter_riverpod 3.3.1`
2. Apply the same pattern to `createGoal()` and `reorderWorkout()` for consistency
3. In `refresh()`, also guard with `ref.mounted` check

```dart
// In Goals notifier:
Future<void> deleteGoal(String id) async {
  final repo = ref.read(goalRepositoryProvider);
  await repo.deleteGoal(id);
  if (!ref.mounted) return;
  await refresh();
}

Future<void> refresh() async {
  if (!ref.mounted) return;
  state = const AsyncValue.loading();
  final repo = ref.read(goalRepositoryProvider);
  state = await AsyncValue.guard(repo.listGoals);
}
```

The calling code in `goal_detail_screen.dart:56-65` already uses `context.mounted` checks (line 58) — no changes needed there. The `ref` in `goal_detail_screen` is a `WidgetRef` (not `Ref`), so `ref.mounted` isn't applicable; the existing `context.mounted` guard is correct.

**Verification:** Delete a goal, navigate away during deletion, verify no crash.

### 1.3 Back Navigation in Plan View Exits App
**Priority:** HIGH
**Bug:** Using the back gesture on `/plan` exits the app instead of navigating to the previous screen.
**Root Cause:** `/plan` is the root route of a `StatefulShellBranch` (line 248 of `app_router.dart`). There is no route below it in that branch, so `PopScope` / system back navigates up to the root, which exits the app.

**Files to modify:**
- `flutter/lib/presentation/screens/plan/plan_screen.dart`

**Implementation:**
1. Wrap `_PlanContent`'s `Scaffold` with `PopScope(canPop: false, onPopInvokedWithResult: ...)` to intercept back navigation. `PopScope` is available (Flutter 3.41.6, already used in `onboarding_wizard_screen.dart` and `barcode_scanner_screen.dart`)
2. When back is pressed on plan view, switch to the Dashboard tab instead of exiting:
   ```dart
   PopScope(
     canPop: false,
     onPopInvokedWithResult: (didPop, _) {
       if (!didPop) {
         GoRouter.of(context).go('/dashboard');
       }
     },
     child: Scaffold(...)
   )
   ```
3. **WARNING:** Do NOT apply this to ALL tab root screens automatically. The `AppShell` widget uses `StatefulShellRoute.indexedStack` which manages its own navigation. Only the plan screen has this reported bug. Adding `PopScope(canPop: false)` to other tabs could break standard Android back behavior where exiting from the root is expected. Only add `PopScope` to other tabs if the same bug is confirmed there.

**Verification:** Press back gesture on Plan tab, verify it switches to Dashboard. Press back on Dashboard, verify it exits app normally.

### 1.4 Water Goal Default Shows 2500L Instead of 2.5L
**Priority:** HIGH
**Bug:** Default water goal shows as "2500L" instead of a reasonable "2.5L"
**Root Cause Analysis:**
- The exact bug is in `health_models.dart:251` — the `NutritionTargets.fromJson` factory:
  ```dart
  water: ((json['waterGoalMl'] ?? json['water'] ?? NutritionTargets.defaults.water) as num).toDouble(),
  ```
  When the API returns `{"waterGoalMl": 2500}`, the `water` field gets the raw mL value (2500) without converting to liters.
- The `water` field is displayed as liters in `_WaterTracker` (`nutrition_screen.dart:541`): `'${currentWater.toStringAsFixed(2)}L / ${waterGoal.toStringAsFixed(1)}L'`
- The `CircularGauge` for water uses `maxValue: targets.water` which would be 2500 instead of 2.5
- Default constants in both `health_entities.dart:650` and `health_models.dart:260` have `water: 3.0` and `waterGoalMl: 3000`

**Data flow:** API → `health_models.dart:251` (fromJson assigns raw mL to `water` field) → `health_mappers.dart:248` (passes through as-is) → `nutrition_targets_provider.dart` → UI displays as liters

**Files to modify:**
- `flutter/lib/data/models/health_models.dart` (line 251 — the exact fix location)
- `flutter/lib/domain/entities/health_entities.dart` (defaults alignment)
- `flutter/lib/data/models/health_models.dart` (defaults alignment)

**Implementation:**
1. Fix `health_models.dart:251` to convert `waterGoalMl` to liters:
   ```dart
   water: json.containsKey('waterGoalMl')
       ? ((json['waterGoalMl'] as num).toDouble() / 1000)
       : ((json['water'] ?? NutritionTargets.defaults.water) as num).toDouble(),
   ```
   This avoids the ambiguity of using `??` between mL and L values.
2. Change default `water` from `3.0` to `2.5` in both `health_entities.dart` and `health_models.dart`
3. Change default `waterGoalMl` from `3000` to `2500` in `health_entities.dart`
4. Add a safety clamp in the UI to prevent displaying unreasonable values (>10L should be treated as mL and divided by 1000)
5. Verify the `toJson()` in `health_models.dart:285` sends `water` back in the correct unit (liters)

**Verification:** Fresh install shows 2.5L default. Existing data showing 2500 is corrected.

### What Was Wrong/Missing in the Original Plan

#### New Bug Found: DropdownButtonFormField `initialValue` (1.2b)
**Critical miss.** `plan_screen.dart:820` uses `initialValue: _selectedType` on a `DropdownButtonFormField`. This parameter does NOT set the selected dropdown value — `value` does. The workout type dropdown never shows the current selection when editing. Added as **1.2b** with HIGH priority.

#### Water Bug Root Cause Was Imprecise
The original plan said "check the mapper" but didn't identify the **exact line**. Traced the full data flow:
- `health_models.dart:251`: `water: ((json['waterGoalMl'] ?? json['water'] ?? ...) as num).toDouble()`
- When API returns `{"waterGoalMl": 2500}`, the `??` chain picks the mL value and assigns it directly to the `water` field (which should be in liters)
- Fix: Use `json.containsKey('waterGoalMl')` check and divide by 1000, rather than relying on `??` which conflates two different units

#### `ref.mounted` Availability — Confirmed Safe
`flutter_riverpod 3.3.1` supports `ref.mounted`. The codebase already uses `PopScope` (Flutter 3.41.6). Both are safe to use.

#### Back Navigation (1.3) — Plan Was Too Aggressive
The original plan said to apply `PopScope(canPop: false)` to ALL tab root screens. This is **dangerous** — standard Android behavior expects back-from-root to exit the app. Only the plan screen has this reported bug. Changed recommendation to apply only where the bug is confirmed.

#### `goal_detail_screen.dart` Guard — Plan Was Incorrect
The original plan said to add `ref.mounted` checks in `goal_detail_screen.dart:56-65`. But that screen uses a `WidgetRef` (from `ConsumerWidget`), not a `Ref` (from a Riverpod notifier). `ref.mounted` is a `Ref` concept. The existing `context.mounted` check at line 58 is the correct pattern. Removed the incorrect instruction.

#### Notification Service Missing Methods
The plan proposed `cancelAllReminders()` but `NotificationService` has **no cancel methods at all**. Added prerequisite section (5.1.0) to add `cancelAllNotifications()` and `cancelNotification()` to both the interface and implementation before any scheduling work begins.

#### Android 13+ Permission Gap
The notification plan didn't mention `POST_NOTIFICATIONS` permission. `flutter_local_notifications 21.0.0` with `AndroidScheduleMode.exactAllowWhileIdle` requires explicit permission on Android 13+. Added to prerequisites.

#### Stack Take-All Race Condition Risk
Original plan used sequential `await` in a loop for stack take-all. This would cause N provider invalidations and N UI rebuilds. Changed to `Future.wait` for parallel execution, with a note to consider a dedicated `toggleAll()` batch method.

#### Marathon Shape Graph (2.2) — Missing Data Source
`AnalyticsStats` only has a single `marathonShape` value, not historical data. The plan didn't identify that a trend chart requires a new data source. Added blocker note and three options.

#### Existing Hardcoded Strings Not Identified

### Additional Concerns

1. **`NutritionTargets.waterTrackingEnabled` (Phase 4.2):** Adding this to the entity changes the schema. If the API doesn't recognize this field, it'll be lost on sync. The plan stores it in SharedPreferences, which is fine for local state, but the `NutritionTargets` entity is also synced via `apiRepo.setNutritionTargets()`. The `toJson()` in `health_models.dart:280-286` doesn't include `waterGoalMl` or `waterTrackingEnabled`, so these are already partial-synced. Consider whether `waterTrackingEnabled` should be purely local (SharedPreferences only, not in the entity).

This class is already at 175 lines. Consider extracting reminder settings into a separate `ReminderSettings` class.
