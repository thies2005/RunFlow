# Plan 14.5: Production-Ready Plan Creation + Safe Workout Sequencing

## Goal

Make plan creation feature-complete across Web Advanced Plan and Flutter while keeping changes minimal, reusing existing components/API behavior where safe, and fixing back-to-back same-type workout generation. Then extend goal time projections to support triathlon, ultra, and backyard ultra race types — both in Web and Flutter.

## Key Decisions

- **Canonical unit for `weeklyMileageGoal`: meters.** Web simple setup already sends `weeklyMileage * 1000`; Flutter must do the same.
- **Do not store `calibrationFactor` on `Goal`.** Prisma has `User.vdotCorrectionFactor`, not `Goal.calibrationFactor`.
- **Do not import sequencing helpers from `index.ts` into generators.** Move the helper to a separate utility file to avoid circular imports.
- **Do not reuse `goalSchema` directly for advanced plans.** It requires `raceType` and `raceDate`; advanced supports `NO_RACE` with null race fields.
- **Use existing Web setup components where practical, but copy required state/query glue from `PlanSetupForm.tsx`.** The components are not plug-and-play without props.
- **Sub-goals remain Web-only.** Flutter wizard does not support sub-goals. Only per-goal-type time projections (triathlon/backyard/ultra) will be added to Flutter.
- **Triathlon time estimation uses VDOT-based heuristic only.** No fetching of past swim/bike activities from Strava. Uses existing `estimateSwimPaceFromVdot()` + `estimateBikeFtpFromVdot()` + run time prediction.
- **Backyard ultra: user chooses loop distance freely.** No default — must be entered. Target laps via slider (1–100).
- **Triathlon goal slider: total time slider + expandable read-only splits.** Total finish time is the primary slider. Swim/bike/run/t1/t2 splits shown in a read-only expandable section. Manual override replaces the entire slider with a single total-time text entry — no per-split editing to avoid partial-override state management complexity.
- **Full Flutter `RaceType` enum expansion to all 17 values in one shot.** Not incremental.
- **Flutter onboarding update is a required dependency of D8** — not a risk note. `race_goal_step.dart` iterates `RaceType.values` and MUST be updated to grouped display in the same PR.
- **B-gap fixes (calibrationFactor range, maxLongRunKm cap) are in-scope** for this iteration.

### D1. Backend: `estimateTriathlonTime()` utility

**File:** `Web/src/lib/plans/triathlon-time.ts` (new)

**Input:**
```typescript
interface TriathlonTimeInput {
    vdot: number;
    raceType: RaceType;
    customSwimDistM?: number;
    customBikeDistM?: number;
    customRunDistM?: number;
}

interface TriathlonTimeResult {
    totalSeconds: number;
    swimSeconds: number;
    bikeSeconds: number;
    runSeconds: number;
    t1Seconds: number;
    t2Seconds: number;
}

interface TriathlonTimeProjection {
    optimal: TriathlonTimeResult;
    projected: TriathlonTimeResult;
    conservative: TriathlonTimeResult;
}
```

**Algorithm:**

1. **Look up distances** from `TRI_RACE_*` constants in `triathlon.ts`. If any `custom*DistM` override is provided and > 0, use it instead of the default. If a custom override is 0 or null/undefined, fall back to the race type default — never use 0.

2. **Swim split**: `estimateSwimPaceFromVdot(vdot)` → returns sec/100m → multiply by `swimDistM / 100`

3. **Bike split**: `estimateBikeFtpFromVdot(vdot)` → FTP watts → `bikePowerToSpeed()` → bike distance / speed
   ```typescript
   // Flat-road cycling power-speed model
   // P = Crr*m*g*v + 0.5*CdA*rho*v^3
   // Simplified: v^3 ≈ watts / 38 → v ≈ (watts/38)^(1/3)
   // At 250W → ~1.87 m/s ≈ 40 km/h (reasonable for Olympic tri bike)
   function bikePowerToSpeed(watts: number): number {
       return Math.pow(watts / 38, 1 / 3);
   }
   ```
   - Race power: `ftp * 0.75` (triathlon race pace is 72-80% FTP; 0.75 is a safe midpoint)
   - `bikeSeconds = bikeDistM / bikePowerToSpeed(ftp * 0.75)`

4. **Run split**: `predictRaceTime(vdot, runDistM)` → seconds (already exists)

5. **Transition times** (fixed by race type, realistic medians for general audience):
   - Sprint: T1=120s, T2=90s
   - Olympic: T1=150s, T2=120s
   - Half Ironman: T1=330s, T2=210s
   - Full Ironman: T1=510s, T2=360s
   - Custom: T1=150s, T2=120s

6. **Three tiers** (fatigue multipliers adjusted for long-course run degradation):
   - **Optimal**: 100% of all estimates
   - **Projected**: +5% swim, +8% bike, +10% run (short course: sprint/olympic)
   - **Conservative**: +10% swim, +15% bike, +20% run (short course: sprint/olympic)
   - For HALF_IRONMAN and FULL_IRONMAN, run degradation is larger due to accumulated fatigue:
     - **Projected**: +5% swim, +8% bike, +15% run
     - **Conservative**: +10% swim, +15% bike, +25% run

7. **Total** = swim + bike + run + T1 + T2, with multipliers applied per-discipline before summing.

8. Return `TriathlonTimeProjection`

**Label in UI:** "Estimated based on running fitness — actual time depends on swim technique, bike handling, and race conditions"

### D2. Backend: `estimateBackyardUltraTime()` utility

**File:** `Web/src/lib/plans/backyard-time.ts` (new)

**Input:**
```typescript
interface BackyardTimeInput {
    vdot: number;
    loopDistM: number;
    targetLaps: number;
}

interface BackyardTimeResult {
    perLoopSeconds: number;
    totalSeconds: number;
    totalDistM: number;
    targetLaps: number;
}

interface BackyardTimeProjection {
    optimal: BackyardTimeResult;
    projected: BackyardTimeResult;
    conservative: BackyardTimeResult;
}
```

**Algorithm:**

1. **Base per-loop time**: `predictRaceTime(vdot, loopDistM)` — loop distance is the "race distance"

2. **Fatigue model** — additive per-lap, not compounding. Laps 1-3 have no fatigue premium; subsequent laps add a fixed percentage:
   ```typescript
   function totalBackyardTime(baseLoop: number, laps: number, fatiguePerLapPct: number): number {
       let total = 0;
       for (let i = 1; i <= laps; i++) {
           const factor = i <= 3 ? 1.0 : 1.0 + ((i - 3) * fatiguePerLapPct);
           total += baseLoop * factor;
       }
       return total;
   }
   ```
   - **Optimal**: `totalBackyardTime(baseLoop, laps, 0.01)` — 1% per lap after lap 3
   - **Projected**: `totalBackyardTime(baseLoop, laps, 0.02)` — 2% per lap after lap 3
   - **Conservative**: `totalBackyardTime(baseLoop, laps, 0.04)` — 4% per lap after lap 3

3. **Total distance**: `loopDistM × targetLaps`
   - Note: This assumes constant lap distance (true for standard backyard format). Does not account for assisted/partial final lap formats — noted in JSDoc.

4. **`perLoopSeconds`** in the result = base per-loop time (no fatigue applied — used for display/pace info)

5. Return `BackyardTimeProjection`

**Validation guard**: Caller must ensure `loopDistM > 0` and `targetLaps >= 1`. Return `null` or throw if invalid.

### D3. Backend: Extend goal time projection for ultra distances

**File:** `Web/src/lib/metrics/goalProjection.ts` (modify)

**Current limitation:** `RaceDistance` type is `'5K' | '10K' | 'HALF' | 'MARATHON'`. Ultra distances are not supported.

**Approach:** Do NOT extend the `RaceDistance` type (tightly coupled to VDOT tables). Add a new function that handles any numeric distance:

```typescript
export function calculateProjectedGoalTimeForDistance(
    currentVO2max: number,
    settings: {
        durationWeeks: number;
        runsPerWeek: number;
        weeklyMileageGoal?: number;
    },
    distanceMeters: number,
    currentShapePercent?: number,    // optional, for consistency with existing function
): { optimalTime: number; projectedTime: number; conservativeTime: number }
```

This reuses the same `progressionFactor` logic from `calculateProjectedGoalTime()` but uses `predictRaceTime(projectedVdot, distanceMeters)` instead of the hardcoded `RaceDistance` lookup. Works for any distance: 50K, 100K, 100M, custom, etc.

**`currentShapePercent` is critical** — without it, ultra projections will be more optimistic than marathon projections for the same user (inconsistent). Default to 70 if not provided (matching existing function's default).

**Timed events (12h/24h):** Add a stub/placeholder function for future use:
```typescript
export function calculateProjectedDistanceForTime(
    currentVO2max: number,
    settings: { durationWeeks: number; runsPerWeek: number; weeklyMileageGoal?: number },
    targetTimeSeconds: number,
): { estimatedDistanceM: number }
```
This is not UI-blocked and can be deferred, but the function signature should exist now to avoid a second migration. Implementation: estimate pace from projected VDOT, multiply by target time.

### D11. Flutter: Port swim-pace and bike-zones heuristics

**File:** `flutter/lib/core/utils/triathlon_estimator.dart` (new)

Port the VDOT-based estimation functions to Dart for client-side triathlon time prediction:

```dart
// From swim-pace.ts
double estimateSwimPaceFromVdot(double vdot) {
    final easyPaceSecPerKm = 360 + (60 - vdot) * 5.5;
    final css = (easyPaceSecPerKm / 10 * 1.4).round();
    return css.clamp(60, 180).toDouble(); // sec/100m, default 120
}

// From bike-zones.ts
double estimateBikeFtpFromVdot(double vdot) {
    final baseFTP = 1.8 + vdot * 0.62;
    return baseFTP.clamp(100, 450); // watts
}

// From D1 algorithm
double bikePowerToSpeed(double watts) {
    return math.pow(watts / 38, 1 / 3); // m/s
}
```

Plus transition time maps and fatigue-tier logic (same as D1/D2).

This avoids needing to fetch estimations from the backend — all computed client-side from the user's VO2max.
