# Plan: Add `startWeeklyMileage` to Plan Setup

## Problem

When RunFlow generates a training plan, the starting volume is always `peakVolume × 0.60` (with a 15km global minimum). This ignores the user's actual current running volume. A half marathon plan with 40km peak always starts week 1 at ~24km, regardless of whether the user currently runs 10km or 30km per week.

## Solution

Add a `startWeeklyMileage` field to plan setup:
- **Defaults** to the user's average weekly running distance over the past 3 months (computed server-side from stored activities)
- **Manual override** via a new slider in both plan creation wizards
- **Race-type-dependent minimums** (e.g., 8km for 5K, 15km for marathon)
- **Applies to all 4 plan generators** (standard, ultra, triathlon, no-race)

## Design Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| User's average > 60% of peak? | Use user's actual average | They've earned the higher start |
| Where to compute default | Server-side | More reliable, works for web too, server already has all activities in Prisma |
| Minimum starting mileage | Race-type-dependent | Aligns with race demands |
| Scope | All plan types | The startVolume logic is identical across all 4 generators |

```ts
export function getMinStartVolume(raceType: RaceType | null): number {
```

### Part 3: Server — Compute 3-Month Average from Activities

**File**: `Web/src/lib/services/plan-creation.ts`

Add `resolveStartWeeklyMileage()` function. Uses actual calendar weeks in the period rather than hardcoded 12, consistent with `AnalyticsService` patterns.

```ts
export async function resolveStartWeeklyMileage(
    userId: string,
    providedValue: number | null | undefined,
    raceType: RaceType | null,
): Promise<number> {
    const minStart = getMinStartVolume(raceType);

    // If user explicitly provided a value via the slider, use it (clamped to minStart)
    if (providedValue && providedValue > 0) {
        return Math.max(providedValue, minStart);
    }

    // Otherwise compute from last 84 days (12 weeks) of RUN activities
    const twelveWeeksAgo = new Date();
    twelveWeeksAgo.setDate(twelveWeeksAgo.getDate() - 84);

    const result = await prisma.activity.aggregate({
        where: {
            userId,
            type: 'RUN',
            startDate: { gte: twelveWeeksAgo },
        },
        _sum: { distance: true },
    });

    // Prisma _sum.distance is number | null — null when no activities exist
    const totalDistanceMeters = result._sum.distance ?? 0;

    // Use actual number of calendar weeks for accuracy
    // (handles partial weeks, user who started running recently, etc.)
    const monday = (date: Date) => {
        const d = new Date(date);
        const day = d.getDay();
        const diff = day === 0 ? -6 : 1 - day;
        d.setDate(d.getDate() + diff);
        d.setHours(0, 0, 0, 0);
        return d;
    };
    const periodStart = monday(twelveWeeksAgo);
    const periodEnd = monday(new Date());
    const weeksInPeriod = Math.max(
        1,
        Math.round((periodEnd.getTime() - periodStart.getTime()) / (7 * 24 * 60 * 60 * 1000))
    );
    const avgWeeklyMeters = totalDistanceMeters / weeksInPeriod;

    return Math.max(avgWeeklyMeters, minStart);
}
```

> **Design note**: We divide by the number of calendar weeks in the period. This means a user who only ran for 4 of the last 12 weeks will get a lower average, which is conservative and correct — they genuinely haven't been running much.

### Part 4: Server — Expose `avgWeeklyKmLast3Months` in Analytics API

**Files**:

- `Web/src/app/api/mobile/v1/dashboard/route.ts`

Add the computed 3-month average to the dashboard response, so the Flutter client can display it as the slider default. Use the same week-counting logic as Part 3 to avoid drift between server default and UI display.

Reuse the same query logic as Part 3. Add alongside existing `currentWeekMileage` calculation.

```ts
// Compute 3-month average weekly running distance
const twelveWeeksAgo = new Date();
twelveWeeksAgo.setDate(twelveWeeksAgo.getDate() - 84);
const threeMonthResult = await prisma.activity.aggregate({
    where: {
        userId,
        type: 'RUN',
        startDate: { gte: twelveWeeksAgo },
    },
    _sum: { distance: true },
});
const avgWeeklyKmLast3Months = Math.round(((threeMonthResult._sum.distance ?? 0) / weeksInPeriod / 1000) * 10) / 10;
```

> **⚠️ Cache key bump**: The web dashboard uses Redis cache with key `dashboard:v2:{userId}:{date}`. Bump to `dashboard:v3:{userId}:{date}` so existing cached responses (without `avgWeeklyKmLast3Months`) are invalidated. The mobile endpoint does not use this cache.


**New code** (replaces both patterns — identical for all 4 generators):
```ts
const minStart = getMinStartVolume(config.raceType ?? null);
let startVolume: number;
if (config.startWeeklyMileage && config.startWeeklyMileage > 0) {
    startVolume = Math.max(config.startWeeklyMileage, minStart);
    startVolume = Math.min(startVolume, peakVolume);
} else {
    startVolume = peakVolume * PLAN_CONSTANTS.START_VOLUME_RATIO;
    if (startVolume < minStart) {
        startVolume = Math.min(minStart, peakVolume);
    }
}
```
