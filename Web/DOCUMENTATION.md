## 1. Project Overview

RunFlow is a self-hosted **multi-sport training platform** for runners, cyclists, swimmers and triathletes. It combines AI-assisted training planning with deep performance analytics and health-based readiness.

Core capabilities:

- **Activity sync** from Strava (OAuth + webhooks, including watts streams), Health Connect (via the Android app), and manual entry.
- **Training plans** for **17 race types** — road (5K→marathon), ultras (50K→24-hour, backyard ultra, custom distance), and triathlon (sprint→Ironman, custom) — generated by the plan engine in `src/lib/plans/`.
- **Structured Workouts v2**: per-step targets (pace / HR / power / RPE), nested repeat groups, planned TSS, and `.zwo` export for Zwift/MyWhoosh.
- **Analytics**: Daniels VDOT & race predictions, two-metric VO2max calibration, TRIMP load, run/bike PMC (CTL/ATL/TSB), cycling power analytics (eFTP, MMP curves, NP/IF/VI, efficiency factor, decoupling).
- **Health & readiness**: daily health logs (RHR, HRV, sleep), body composition, nutrition, supplements, fasting — feeding a daily readiness model with adapted-workout recommendations.
- **AI coach**: multi-provider chat and activity feedback with bring-your-own-key, metering and daily quotas.
- **MCP servers**: use RunFlow from Claude, Gemini or any MCP client (private coaching server + public stateless plan generator).
- **Mobile**: native Kotlin/Compose Android app (`android/`) speaking a JWT API at `/api/mobile/v1`.

  - Next.js 15 (App Router, standalone output, Turbopack dev)

`Activity` stores one synced workout with summary metrics, HR zone time distribution (7 zones), raw Strava payload, and streams (`time/hr/distance/altitude/velocity/watts` as JSON). Cycling additions:

```prisma

```

`DailyFitness` caches the per-day PMC numbers — **run and bike are tracked separately**:

```prisma
ctl, atl, tsb, ctlRunning       // run side (TRIMP / rTSS driven)
trimp, runningTss               // daily load inputs
bikeTss, ctlBike, atlBike, tsbBike  // ride side (bike TSS driven)
@@unique([userId, date])
```

`Workout` is one scheduled session. Besides the classic fields (`workoutType`, `description`, `targetDistance/Duration/Pace/HrZone`) it carries the v2 surface:

Supporting models: `RaceResult`, `PlanSnapshot` (mobile offline plans), `WeekTemplate` / `WorkoutTemplate` (reusable blocks; seeded via `npm run seed:templates`), `IntervalProgression`, `PlanPaceProfile`, `GuidedPlanSession`.

## 4. Metrics & Calculations

### 4.1 VDOT (Daniels)

**Source**: `src/lib/metrics/vdot.ts` — Daniels-Gilbert formula:

```
VO2      = -4.60 + 0.182258·v + 0.000104·v²          (v = velocity, m/min)
%VO2max  = 0.8 + 0.1894393·e^(−0.012778·t) + 0.2989558·e^(−0.1932605·t)
VDOT     = VO2 / %VO2max                              (t = time, min)
```

Produces race predictions across all distances and the five training paces:

| Pace | %VO2max | Purpose |
|------|---------|---------|
| E (Easy) | 65–79% | Aerobic base, recovery |
| M (Marathon) | ~78% | Marathon-specific |
| T (Threshold) | 88% | Lactate threshold |
| I (Interval) | 100% | VO2max intervals |
| R (Repetition) | 105% | Speed & economy |

### 4.2 Two-Metric VO2max

RunFlow tracks VO2max from two independent sources and calibrates both:

1. **Effective VO2max** (`lib/metrics/effectiveVdot.ts`): best-effort estimate derived from the athlete's own activities (90-day lookback, efforts ≥ 5 km, floor of 20) — this is the "what your training says" number.
2. **Swain HR-based VO2max** (`lib/metrics/runalyze.ts` + `lib/metrics/calibration.ts`): current-fitness estimate from HR response, refined by race-shape penalty calibration — the "what your races say" anchor.

Each has its own correction factor on `User` (`effectiveVo2maxCorrectionFactor`, `vdotCorrectionFactor`). The UI labels both consistently; the plan engine uses the calibrated values for pacing.

### 4.3 Fitness Metrics (PMC: CTL/ATL/TSB)

**Source**: `src/lib/metrics/fitness.ts` — Banister impulse-response model:

```
CTL (fitness) = 42-day EWMA of daily load     decay e^(−1/42)
ATL (fatigue) = 7-day EWMA of daily load      decay e^(−1/7)
TSB (form)    = CTL − ATL
```

Run and bike are computed **in parallel** (`ctl/atl/tsb` from TRIMP & rTSS; `ctlBike/atlBike/tsbBike` from bike TSS) and stored on `DailyFitness`. Analytics shows split and combined PMC curves.

TSB interpretation: ≥ +25 peaked · +5…+24 fresh · −10…+4 neutral (productive training) · −30…−11 fatigued · < −30 overtraining risk.

### 4.4 TRIMP

**Source**: `src/lib/metrics/trimp.ts` (Runalyze-style):

```
TRIMP = minutes × HRratio × 0.64 · e^(1.92 × HRratio)
HRratio = (HR_avg − HR_rest) / (HR_max − HR_rest)
```

### 4.5 Running TSS

```
rTSS = duration_hours × IF² × 100        IF = threshold_pace / actual_pace (sec/km)
```

Run-type activities contribute rTSS + TRIMP; rides contribute bike TSS; other sports contribute TRIMP only (unless *include cross-training* is enabled for CTL).

### 4.6 Cycling Power Analytics

**Sources**: `src/lib/metrics/power.ts`, `src/lib/metrics/cyclingAnalytics.ts`

- **Normalized Power (NP)**: 30-second rolling average, raised to the 4th power, re-averaged, 4th root — captures the physiological cost of variable efforts.
- **Intensity Factor (IF)** = NP / FTP · **Variability Index (VI)** = NP / avg watts.
- **Bike TSS** = `duration_h × IF² × 100` — drives the bike side of the PMC.
- **eFTP**: dynamic functional threshold power estimated from best efforts (with `User.ftpWatts` override and `autoEstimateFtp`).
- **MMP power curve**: mean-maximal power from 5 s to 3600 s across all rides; powers FTP estimation and critical-power views.
- **Efficiency Factor** = NP / avg HR; **Aerobic Decoupling** = HR-drift over the second half vs the first — both track aerobic durability.
- Power zone distribution uses the 7 Coggan zones (`lib/metrics/bike-zones.ts`).

Cycling analytics are computed server-side (`cyclingAnalytics.ts` is deliberately isolated so Prisma never enters the client bundle) and exposed via `/api/analytics/cycling` and the Android Cycling tab.

### 4.7 Marathon Shape

A 0–100 readiness score for marathon-specific fitness combining mileage, long-run and cross-training components (`runalyze.ts`); used in race predictions and calibration.

## 5. Structured Workouts v2

**Source**: `src/lib/plans/structured.ts` (Zod schema), design doc: [`docs/archive/structured-workout-schema-v2-design.md`](../docs/archive/structured-workout-schema-v2-design.md) (archived design; the implementation is authoritative).

A workout's `structuredSteps` JSON is a tree of steps and repeat groups:

- **Step kinds**: `warmup | work | recovery | cooldown | steady | transition`.
- **RepeatGroup**: nested repeats up to **depth 3**, iteration counts ≤ 100.
- **Durations**: `time` (seconds) · `distance` (meters) · `lap_press` (manual lap button on the guided player).
- **Targets** per step: pace, HR (zone or bpm range, optional secondary zone), power (watts, %FTP, or zone), cadence (rpm), RPE, or free.
- **Pace units are sport-aware**: running targets are **sec/km**, swim targets are **sec/100m** — the same numeric columns, explicit units in the schema.
- Safety caps: flattened step count limited to `MAX_FLATTENED_STEPS = 500`.

Consumers:

- **Web**: `/plan-advanced` studio editor (drag-and-drop, phase blocks, live planned TSS/PMC projection), guided sessions, `.zwo` export.
- **Android**: `StructuredWorkoutV2.kt` parser with web-parity unit tests; the guided player enforces per-step ranges and supports manual laps.
- **Zwift/MyWhoosh**: `lib/plans/zwo-export.ts` emits compatible `.zwo` files; `mywhooshMatcher.ts` matches a plan's workouts against the MyWhoosh library (`src/data/mywhoosh_workouts.json`) when `User.matchToMyWhoosh` is enabled.

## 7. Strava Integration

**Source**: `src/lib/strava/`

### 7.1 OAuth Flow

1. User clicks "Connect with Strava" → Strava authorization page
2. User approves → callback with code → NextAuth exchanges for tokens
3. Tokens stored on `User` (encrypted at rest with `ENCRYPTION_KEY`)

Scopes: `read:activity`, `activity:read_all`, `profile:read_all`. Strava access tokens expire after ~6 hours; `lib/strava/oauth.ts` refreshes transparently and retries.

### 7.2 Webhook Setup

Strava has no UI for webhook subscription — use the API:

```bash
curl -X POST https://www.strava.com/api/v3/push_subscriptions \
  -d client_id=YOUR_CLIENT_ID -d client_secret=YOUR_CLIENT_SECRET \
  -d callback_url=https://your-domain.com/api/webhooks/strava \
  -d verify_token=YOUR_VERIFY_TOKEN
```

Handle `create` / `update` / `delete` events; `GET` on the same endpoint verifies the subscription. The webhook URL must be publicly reachable.

### 7.3 Sync Behavior

- Full sync fetches activities with streams — including **watts streams** for rides, which feed the power engine.
- Syncs are queued and rate-limited (Strava: 100 req/15 min standard, 1000 premium) with exponential backoff.
- `autoSync.ts` keeps data fresh opportunistically; the webhook triggers near-real-time ingestion.

## 8. Training Plans

**Source**: `src/lib/plans/` — the **only** plan engine (the classic on-device Daniels engine was removed in v2.3.0; the Android app uses this engine server-side, or its on-device port when offline).

### 8.1 Race Types & Phases

Plans exist for all 17 `RaceType` values: road (5K–marathon), ultras (50K–24 h, backyard ultra, custom distance) and triathlon (sprint–Ironman, custom). Triathlon plans schedule swim/bike/run/strength plus brick and transition-practice sessions; timing models include triathlon transitions (`triathlon-time.ts`), swim pace (`swim-pace.ts`) and backyard-ultra projections (`backyard-time.ts`).

Phases follow a periodized arc (`PlanPhase`): **BASE → BUILD → PEAK → TAPER → RACE_WEEK**, with **RECOVERY** phases after completion; phase composition can be expressed as **phase blocks** (v2) that the studio editor manipulates directly.

### 8.2 Generation Inputs

1. Athlete metrics — calibrated VDOT/VO2max (two-metric system), thresholds, HR zones, FTP, swim CSS
2. Race type & date, target time
3. Volume: `planWeeks`, weekly mileage goal, per-sport frequency (`runsPerWeek`, `ridesPerWeek`, `swimsPerWeek`, `strengthPerWeek`)
4. Phase lengths and preferred training days / rest days

Output: `Goal` + `Workout` rows with phases, paces, range targets, structured steps and `plannedTss`. `adaptPlanAfterCompletion` folds a race result back into the plan; `recalculate-paces.ts` re-paces an entire plan after threshold changes.

### 8.3 Plan UIs

- **`/calendar`** — the day-to-day view for executing a plan: minimal pills, drag-reschedule, slide-over detail drawer. (The old `/plan` week-list redirects here.)
- **`/plan-advanced`** — the studio: v2 structured editor, engine-backed generator, phase blocks, week copy/paste, drag-and-drop, live planned-TSS/PMC projection.
- **`/plan-generator`** — wizard that walks through race options.

## 9. MCP (Model Context Protocol)

RunFlow exposes **two MCP servers** at the app root (not under `/api`). Full tool schemas, OAuth setup and client walkthroughs: **[`docs/MCP_API.md`](../docs/MCP_API.md)**.

| | Private `/mcp` | Public `/mcp/public` |
|---|---|---|
| Audience | Paid-Premium users | Anyone |
| Auth | OAuth 2.1 + PKCE (+ RFC 7591 dynamic client registration), or `rf_` API key | none (stateless) |
| Rate limit | per-user async limits | 10 requests/hour/client |
| Tools (16) | `get_athlete_profile`, `get_fitness_metrics`, `get_cycling_analytics`, `get_training_plan`, `get_recent_activities`, `get_readiness_and_health`, `create_training_plan`, `update_training_plan_phases`, `create_structured_workout`, `modify_workout`, `reschedule_workout`, `swap_workouts`, `delete_workout`, `mark_workout_status`, `recalibrate_thresholds`, `save_weekly_coaching_summary` | 3: `generate_running_plan`, `calculate_vdot_paces`, `export_plan_url` |

Safety: mutating plan tools pass `evaluatePlanSafety` (`lib/mcp/safety.ts` — weekly-volume spike, long-run cap, consecutive hard days, projected TSB overload) and snapshot plans before changes. OAuth tokens are stored hashed only; codes are single-use with PKCE S256; refresh tokens rotate and can be revoked.

TypeScript strict mode, ESLint (Next.js config). `npm run lint` / `npm run lint -- --fix`. Conventions: see [`CODING_STANDARDS.md`](../CODING_STANDARDS.md).

### 10.6 Adding a New Metric

1. Implement the calculation in `src/lib/metrics/` (pure function, no Prisma imports if it might run client-side)
2. Add types in `src/types/`
3. Wire it into the analytics service or the relevant API route
4. Add a Prisma field if it should be cached (schema + migration + regenerated client)
5. Add unit tests; extend the UI and/or MCP tool output as needed

## 12. Troubleshooting

**Activities not syncing from Strava** — check `stravaTokenExpiry` on the user, trigger a manual sync, verify the webhook subscription (curl from §7.2), and confirm rate limits weren't exhausted (wait 15 min).

**VDOT / VO2max looks wrong** — ensure activities carry HR data, verify HR zones in settings, check both correction factors (classic VDOT and effective VO2max), and calibrate with a known race result.

**Database connection errors** — `docker compose ps`, `docker compose logs db`, verify `DATABASE_URL`, restart `db`.

**Docker build fails** — `docker builder prune -a`, check disk space and network, retry with `--no-cache`; on memory-constrained builders check the note in §11.4.

**Webhook validation fails** — `STRAVA_VERIFY_TOKEN` must match the subscription, the URL must be publicly reachable, and the Strava app's callback domain must be correct.

**MCP client can't connect** — the endpoint is at the app root (`/mcp`, `/mcp/public`), redirect URIs must be registered (dynamic registration handles Claude/Gemini), and behind a proxy the resolved public origin must be correct (falls back to `NEXTAUTH_URL`). See [`docs/MCP_API.md`](../docs/MCP_API.md).

## Appendix A: Formula Reference

```
VDOT (Daniels-Gilbert)
  VO2     = −4.60 + 0.182258·v + 0.000104·v²
  %VO2max = 0.8 + 0.1894393·e^(−0.012778·t) + 0.2989558·e^(−0.1932605·t)
  VDOT    = VO2 / %VO2max

TRIMP (Banister)      TRIMP = t · HRratio · 0.64·e^(1.92·HRratio)
Running TSS           rTSS = t(h) · IF² · 100,   IF = pace_thr / pace_actual
Bike TSS              bikeTSS = t(h) · IF² · 100, IF = NP / FTP
Normalized Power      30 s rolling avg → ^4 → avg → 4th root

PMC                   CTL = EWMA₄₂(load),  ATL = EWMA₇(load),  TSB = CTL − ATL
                      (run & bike tracked independently on DailyFitness)
```
